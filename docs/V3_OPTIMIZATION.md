## 1. V3 总体目标

V3 重点改善日常使用时的界面聚焦、反馈清晰度和功能入口组织方式：

1. 普通对话保持简洁，不被未请求的高级能力入口打断。
2. 能力入口只在相关场景出现，或在用户主动需要时展开。
3. 后端工作流、前端展示和权限审批保持一致，界面提示不能让用户误以为已经执行任务。
4. 继续保留现有审批、授权、核验和安全边界。
5. 每个优化点都记录预期行为、实现范围、验证方式和未覆盖风险。

## 2. 已确认问题

### V3-001：普通问候后显示不相关的能力工作区

**状态**：已完成（本地源码；安装包未重建）
**发现日期**：2026-10-04
**发现方式**：用户在新对话中仅输入“你好”并查看回复。

#### 现象

用户只输入普通问候“你好”时，系统正确回复：

> 你好！有什么可以帮你的吗？

但回复区域下方仍显示以下折叠能力入口：

- 代码生成与网页原型
- 系统清理：旧临时文件隔离
- 脚本、桌面与浏览器执行详情

这些入口与当前问候无关，增加了页面噪声，可能让用户误以为系统已经为这些任务准备了执行状态，或误以为这些功能是每次对话都必须处理的步骤。

#### 当前原因

这是前端展示策略问题，不是本次请求被错误路由：

- apps/desktop/src/renderer/main.tsx 在存在会话时固定渲染 M17Workspace 和 M18Workspace。
- M17 工作区包含代码生成、网页原型和系统清理面板。
- M18 工作区包含脚本、桌面应用和浏览器执行面板。
- 普通问候仍由后端识别为普通回答；这些面板只是被前端静态挂载。
- 面板内部的 details 会根据当前工作流决定是否展开，但外层能力工作区仍会出现在页面中。

因此，当前行为是“后端没有触发任务，但前端始终显示所有高级能力入口”。

#### 期望行为

对于“你好”“谢谢”“继续”“好的”等普通对话：

- 只显示正常对话内容和必要的输入区域。
- 不显示代码生成、系统清理、脚本、桌面或浏览器执行工作区。
- 不创建对应的工作流、审批、授权、执行记录或模型请求。
- 当前会话仍可通过明确需求进入相关能力，不降低已有功能。

对于明确相关请求，例如：

- “帮我生成一个 React 页面”
- “清理当前用户 Temp 中的旧日志”
- “运行这段 Python 脚本”
- “操作这个普通桌面应用”
- “在这个指定网页填写表单”

再显示对应的能力工作区，并保留现有预览、授权、审批和核验流程。

#### 修复策略

采用“按需展示、状态驱动”的方式：

1. **默认隐藏高级工作区**
   - 普通会话初始不显示 M17/M18 工作区。
   - 不以“组件已挂载但折叠”作为隐藏方案，因为折叠标题本身仍会造成干扰。

2. **按工作流显示**
   - 当 conversation.workflow.action 为 development 或 cleanup 时显示 M17 对应区域。
   - 当 action 为 script、desktop 或 browser 时显示 M18 对应区域。
   - 当已有对应的待审批计划、草稿、执行事实或历史恢复状态时，继续显示对应区域，避免用户失去上下文。

3. **主动入口保留**
   - 在用户明确表达相关意图后，后端返回相应工作流，前端再加载对应区域。
   - 如产品后续需要“主动开始某类任务”，提供明确的用户入口，而不是在每个新对话中展示全部能力。

4. **避免误触发副作用**
   - 仅改变渲染和入口可见性，不放宽后端权限检查。
   - 普通问候不能触发模型调用、目录扫描、文件访问、脚本执行、桌面控制或浏览器访问。
   - 组件因历史状态恢复而显示时，仍必须重新满足当前会话授权和审批条件。

#### 涉及文件（预估）

- apps/desktop/src/renderer/main.tsx
- apps/desktop/src/renderer/M17Cards.tsx
- apps/desktop/src/renderer/M18Cards.tsx
- 相关前端单元测试和 E2E 测试
- 本文档及 docs/PROGRESS.md（实施后更新）

实际修改前需再次检查当前组件状态和工作流契约，避免把历史恢复状态与新任务状态混淆。

#### 验收标准

- 新建会话输入“你好”，页面不显示上述三个能力工作区标题。
- 普通问候不产生 M17/M18 相关 IPC 调用。
- 明确代码、清理、脚本、桌面或浏览器需求时，对应工作区能出现并正常使用。
- 工作流进入等待审批、运行、失败、完成和恢复状态时，对应工作区不会意外消失。
- 切换会话后，工作区只跟随当前会话状态，不串到其他会话。
- 现有权限、审批、取消、核验和审计行为不改变。

#### 验证等级

计划至少执行：

- **L0**：TypeScript、静态检查和差异检查。
- **L1**：相关前端组件测试。
- **L2/L3**：普通问候、明确 M17 请求、明确 M18 请求和会话切换流程。

本项修复前不把“组件折叠”视为通过；必须验证普通问候页面实际不出现无关能力入口。

实际修改包括 renderer、快照契约、chat历史投影/本地寒暄、相关测试及模块说明。设计中的“仅前端”经检查扩展为必要的有界只读投影与寒暄处理：原实现中M18挂载自动读取账本，单靠最近消息无法保留被裁剪的历史；原“你好”实际会调用Main。没有修改权限、模型配置或审批策略。

### V3-004：复合请求只执行首步却错误标记为完成

- **状态**：已实施验证，待用户手动推送
- **发现日期**：2026-10-04
- **发现方式**：在已启动的开发版中使用 Computer Use 进行真实桌面复现。
- **测试指令**：
  - 扫描 C 盘垃圾文件并找出占用空间较大的可清理项；
  - 扫描已安装应用并找出长期未使用或从未使用的闲置应用；
  - 分析风险等级并给出清理或保留建议；
  - 输出包含清单、空间、风险和建议的 Doc 文档；
  - 在对话框给出摘要并指出高价值清理项。
- **测试前提**：
  - 新建独立测试对话。
  - 通过原生目录选择器明确授权 C:\。
  - 只允许只读扫描，不批准删除、移动、隔离、重命名或外发。
- **当前现象**：
  1. 系统要求用户授权目录，授权 C:\ 后自动接续原请求。
  2. 实际只执行了目录根的一级扫描。
  3. 结果为发现 21 项、展示 21 项、访问 29 项、深度 1 层；另有 path_denied 1 项和 path_unavailable 7 项。
  4. 结果仅按扩展名和目录属性分类，没有读取正文。
  5. 已安装应用识别、闲置判断、风险分析、清理建议、Doc 生成和对话摘要均未执行。
  6. 会话随后直接显示“已完成”，没有保留未完成步骤，也没有要求拆分或说明不支持。
- **测试收尾**：
  - 已撤销本次测试会话的 C:\ 目录授权。
  - 未删除、移动、隔离、重命名或写入任何用户文件。
  - 未生成 Word 文档。
- **问题判断**：
  - 这是复合请求编排和完成判定问题，不是目录授权失败。
  - 当前系统把首个可识别的目录列表步骤当成了整个请求，或在后续目标无法映射到既有能力时静默丢失了目标。
  - “已安装应用分析”本身也不属于当前已实现的目录扫描能力，不能被伪装成已完成。
- **期望行为**：
  - 系统必须保留原指令中的全部目标和顺序。
  - 如果目标可以拆成多个已实现步骤，应逐步执行，并在每步完成后核验下一步。
  - 如果某个目标没有实现能力，应明确说明“不支持”及原因，不能标记整个请求完成。
  - 如果任务包含高风险或范围不明的操作，应暂停并请求必要授权或澄清。
  - 只有所有目标均完成、明确不支持且用户接受，或用户取消请求时，才能结束会话任务。
- **修复策略**：
  1. 为复合请求保留原始目标清单、步骤顺序和每步状态，不允许只保留首个路由步骤。
  2. 路由结果必须区分“已执行”“等待授权”“等待审批”“不支持”“失败”和“未开始”。
  3. 完成判定改为全步骤判定；首步目录扫描成功不能直接结束包含后续目标的请求。

### V3-005：PDF 总结结果暴露内部解析术语，普通用户难以理解

- **状态**：待确认
- **发现日期**：2026-10-04
- **发现方式**：用户上传 PDF 文献并输入“总结这份文档”，根据实际界面截图反馈。
- **当前现象**：
  - 用户只想上传文献并获得总结，界面却显示“附件解析已返回：请检查提取方式、截断和缺失单元。原文是不可信资料。”
  - 页面直接展示证据 ID、文件版本、读取时间和“本次资料·本地添加不等于云端发送”等内部实现信息。
  - “不可信资料”“内容缺失”“截断单元”等术语没有结合用户问题解释，普通用户不知道是否需要处理，也不知道是否还能继续提问。
  - 用户需要自己理解本地解析、证据版本、上云确认和引用校验等系统概念，打断了“上传文件后直接提问”的主流程。
- **问题判断**：
  - 这些信息属于系统内部的解析、证据和权限状态，不应默认作为主回答内容展示。
  - “资料不可信”是系统对外部内容的安全标记，不等于文件不能阅读，也不等于总结失败；当前文案容易让用户误以为文件无效。
  - 解析缺失或截断确实可能影响回答，但应该由 Agent 在回答中结合实际影响说明，而不是把底层字段原样推给用户。
- **期望行为**：
  1. 用户上传 PDF，输入问题或“总结这份文档”。
  2. 系统在后台完成解析、页码定位、截断检查、引用绑定和必要的完整性判断。
  3. 默认界面直接呈现结构清晰的中文答案，包括摘要、关键发现、方法或结论、局限和引用。
  4. 只有会影响当前问题回答的缺失或解析异常，才用自然语言给出简短提示，例如“第 8 页为图片，相关内容未能读取，以下结论不包含该页”。
  5. 证据 ID、SHA256、文件版本、读取时间、解析方式和权限细节放入“查看来源详情”或高级信息区域，默认折叠。
  6. “不可信资料”改为用户可理解的来源提示，例如“以下内容来自你上传的文件，结论请结合原文核对”；不把安全边界写成阻塞性错误。
  7. 解析成功后不要求用户理解内部状态，除非确实需要用户重新选择文件、补充问题或确认发送范围。
- **修复策略**：
  1. 建立“用户层回答”和“内部证据层”两套展示模型；后端继续保存完整证据与审计字段，前端默认只使用用户层文案。
  2. 将解析状态映射为少量用户可理解的状态：处理中、已准备回答、部分内容无法读取、无法回答。
  3. 只有与当前问题相关且会改变结论的缺失、OCR 失败、页码不可定位或截断，才进入主回答提示；无关的内部字段不显示。
  4. 在回答卡片中优先呈现模型答案和引用位置；来源详情使用可展开区域，不占据主阅读路径。
  5. 模型调用前的发送范围确认仍然保留，但文案改为“将使用以下文件内容回答你的问题”，不要展示内部 schema、哈希和供应商术语。
  6. 模型无法可靠回答时，用“目前无法根据这份文件确认……”说明事实边界，并给出下一步建议，不显示泛化的“资料不可信”。
  7. 对 PDF、DOCX、PPTX 和图片统一这套信息分层，避免不同文档类型出现不同的内部术语。
- **涉及文件（预估）**：
  - apps/desktop/src/renderer/DocumentCards.tsx
  - apps/desktop/src/renderer/SynthesisCards.tsx
  - apps/desktop/src/renderer/main.tsx
  - backend/src/orvia_backend/documents/
  - backend/src/orvia_backend/chat/
  - 相关文案、组件和文档总结 E2E 测试
- **验收标准**：
  - 上传一份可正常解析的 PDF 并输入总结问题后，主区域首先显示易读答案，不显示证据 ID、SHA256、内部版本字段或“原文是不可信资料”。
  - 解析存在局部缺失时，主回答只显示与当前问题相关的简短影响说明。
  - 用户可以通过“查看来源详情”主动查看页码、引用、解析方式和完整性信息。
  - 解析失败时，界面明确说明失败原因和可行下一步，不显示无法理解的底层错误组合。
  - 本地解析、云端发送确认、引用校验和权限边界仍然有效，不因简化文案而放宽安全策略。
  - 同一套展示规则覆盖 PDF、DOCX、PPTX 和图片资料。
- **测试等级与命令**：L1/L2；补充 PDF 正常解析、部分缺失、OCR 不可用和模型总结流程的 L3 验收。
- **已知限制**：高级用户仍可能需要查看完整证据和解析细节，因此这些信息不能删除，只能从默认主流程中移入按需展开区域。
- **讨论结论**：用户确认当前信息暴露方式对普通用户不友好；先确定答案卡片和详情折叠的交互，再进入实现。
